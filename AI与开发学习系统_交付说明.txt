学序网站学习系统新增交付说明
主题：开发流程线 + AI认知线，并与现有开发基础线衔接

一、这次要解决什么

当前已经在进行 vibe coding，但缺少两类系统认识：
1. 不熟悉“一个软件项目应该怎样被合理地开发出来”的完整流程。
2. 对现代 AI / LLM / Agent / 模型评估等缺少系统认知。

因此，不要直接把现有《开发学习方案》中的 01—07 全部学完后才接触 AI，也不要只学 AI 而继续依赖“让模型直接改代码”。

新的学习系统采用三条线：

A. 开发流程线：先建立正确做项目的方法。
B. AI认知线：先建立现代 AI 的知识地图和判断能力。
C. 开发基础线：沿用现有开发学习方案，系统补代码和计算机基础。

核心顺序：
开发流程线 + AI认知线先启动
→ 在保持 vibe coding 实践的同时建立基本地图
→ 再系统推进开发基础线 01—07
→ 基础逐渐稳定后，重新进入 AI 第二遍，学习真正的 AI 应用实现、RAG、Agent、Eval 等。

这不是三套互相独立的课程。

开发流程线回答：“一个项目应该怎么做？”
AI认知线回答：“我现在使用的 AI 是什么、能做什么、怎么判断它？”
开发基础线回答：“代码和计算机为什么这样运行，我怎样逐渐自己理解、修改和维护？”

开发流程线从第一天开始长期贯穿项目。
AI认知线第一遍以理解为主，可以先于完整代码基础。
开发基础线负责逐渐补齐底层能力；随着它推进，再返回 AI 认知线做第二遍实践和深化。


==================================================
二、第一条线：开发流程线
==================================================

目标：
即使目前还不能读懂大量代码，也能以合理、可检查、可恢复的方式使用 AI 开发项目，而不是“描述需求 → AI 随便改 → 能运行就结束”。

第一遍建议做成 7—9 个学习节点，不需要拖成长课程。预计 1—2 周建立基本框架，之后在真实项目里持续使用。

1. 软件开发完整流程

先建立总地图：

想法
→ 明确问题
→ 写需求
→ 写验收标准
→ 设计方案
→ 拆任务
→ 建立版本/分支
→ 实现
→ 检查改动
→ 测试
→ 发布
→ 观察结果
→ 修复或回滚
→ 下一轮迭代

要求：
能够解释每一步解决什么问题，不要求先学会对应的全部代码实现。

2. 需求与验收标准

重点：
- 区分“我想做什么”与“具体要怎样表现”。
- 学会把模糊想法写成可验证的功能要求。
- 每个功能先定义完成标准，再让 AI 开始实现。
- 包含正常情况、错误情况、边界情况。

实践：
直接从序流、学序、sinefine 等现有项目选一个真实小功能，把需求和验收标准写清楚。

完成标准：
以后新增明显功能时，能够先给出简短的需求 + 验收标准，而不是只给 AI 一句模糊描述。

3. 方案设计与任务拆分

重点：
- 先确认“需要改哪些模块、数据放哪里、有哪些风险”，再改代码。
- 理解前端、后端、数据库、外部服务各自大概负责什么。
- 大功能拆成多个可以分别验证的小任务。

不要求：
现在就自己设计复杂系统架构。

完成标准：
能够看懂 AI 给出的方案说明，并判断它是不是明显改得过大、遗漏关键部分或没有验证方式。

4. 项目、环境与版本管理

需要掌握的最低限度：
- 项目目录是什么、当前目录是什么。
- 本地项目、Git 仓库、GitHub、线上部署之间的关系。
- 工作区 → 暂存区 → commit → 远程仓库。
- git status / git diff / git add / git commit / git pull / git push 的用途。
- 修改前后保留可靠版本。
- 知道什么情况下需要回滚。

主资源：
- 《Pro Git》中文版，第 1—3 章，按实际需要选读。
- Microsoft PowerShell 官方文档：路径、目录、常用命令。
- GitHub 官方文档：仓库、commit、branch、pull/push 的基础部分。

辅助方式：
直接使用自己的项目练习，不另做大量脱离实际的小练习。

注意：
第一遍不要强制学习 Docker、SSH、复杂 CI/CD。遇到真实需要时再进入现有开发方案中的对应内容。

5. 与 AI 协作实现

建立固定工作方式：

需求和验收标准
→ 让 AI 先解释方案
→ 确认任务拆分
→ AI 实现
→ 说明修改了哪些文件以及原因
→ 查看 diff
→ 测试
→ 再决定是否 commit / 发布

重点：
当前不要求逐行读懂代码，但必须逐渐做到：
- 知道改了哪些文件。
- 知道每个文件大概为什么改。
- 能追踪主要数据“从哪里来 → 经过哪里 → 到哪里去”。
- 能发现 AI 是否明显修改了无关内容。

6. 测试与验证

先学测试思想，不先学复杂测试框架。

重点：
- 页面能打开不等于功能正确。
- 按验收标准逐条验证。
- 正常输入、错误输入、空输入、重复操作、刷新、网络失败等情况。
- 区分手动测试、自动测试、日志。

主资源：
- pytest Get Started：在后续 Python / 软件工程阶段实际学习自动测试。
- 当前阶段以项目自己的验收清单和手动验证为主。

完成标准：
每次重要功能完成后，不再只凭“看起来能用”判断完成。

7. 发布、观察与回滚

重点理解：
本地代码 → Git commit → GitHub → Vercel/部署平台 → 线上版本。

学会区分：
- 本地代码问题
- Git/GitHub 同步问题
- 构建失败
- 部署失败
- 线上运行错误

真实项目使用什么部署平台，就优先阅读该平台的官方文档。

完成标准：
知道新版本发布后怎么确认结果；出现严重问题时，优先定位或回滚，而不是继续叠加修改。

8. 开发流程线的长期实践模板

建议学序把以下模板作为真实项目中的轻量检查项，而不是复杂的强制表单：

功能：
目的：
验收标准：
方案：
任务拆分：
本次修改：
验证结果：
对应 commit：
是否已发布：
如果出错如何回滚：

不要要求每个微小修改都填完整表格。只有明显功能、重要修复或风险较高的改动使用完整流程。


==================================================
三、第二条线：AI认知线
==================================================

目标：
先建立对现代 AI 的完整地图，理解当前正在使用的模型、Agent 和 coding tools 是什么，并具备基本的模型能力判断能力。

第一遍重“理解”，不要求先训练模型，也不要求一上来自己实现 Agent。

建议分成 6 个模块。

1. AI / LLM 基础地图

内容：
- AI、机器学习、深度学习、生成式 AI、LLM 的关系。
- 参数、token、embedding、上下文窗口。
- Transformer / Attention 的直观作用。
- Dense 与 MoE。
- 预训练、后训练、推理。
- 多模态。
- 开源权重、闭源模型、API、本地模型的区别。

主资源：
- Google Machine Learning Crash Course：Intro to ML、LLM / Embedding 相关概念模块。
- Hugging Face LLM Course：优先第 1—2 章中与 Transformer、模型、Tokenizer 有关的部分。

要求：
第一遍只选读需要的部分，不要求把完整课程从头做到尾。

2. LLM 为什么能工作

内容：
- 神经网络最基本直觉。
- “预测下一个 token”是什么意思。
- loss、训练、参数更新的直观含义。
- Transformer 信息怎样传递。
- 训练与推理的区别。
- 为什么会 hallucination。
- 为什么 context 会改变表现。
- 为什么 post-training 会显著影响模型行为。
- reasoning model / test-time compute 的基本概念。

要求：
先能解释，不要求完整数学推导。

辅助资源：
- Google ML Crash Course 中神经网络相关内容。
- Hugging Face LLM Course 对架构和推理的解释。
- 遇到公式时按需补数学，不要因为数学前置阻塞整个 AI 第一遍。

3. AI 应用系统

内容：
- Prompt 与 Context Engineering。
- Structured Output。
- Tool / Function Calling。
- Embedding。
- RAG。
- Memory。
- MCP。
- Agent。
- Harness / Agent scaffold。
- latency、token、cost。
- 模型、工具、上下文、运行环境之间的分工。

核心理解：
ChatGPT Work、Codex、Claude Code 等不是“一个模型本身”，而是：
模型 + Context + Tools + Harness/Agent workflow + Environment。

主资源：
- Hugging Face AI Agents Course：Unit 1 为主。
- MCP 官方 Architecture Overview。
- 使用具体模型/API 时，优先查对应厂商的官方文档。

第一遍不要求：
- 同时学习多个 Agent 框架。
- 自己实现完整 MCP Server。
- 做复杂 Multi-Agent 系统。

4. 模型能力与评估

这是 AI 认知线的重点模块。

必须建立的认识：
“模型能力”不能只看一个总分。

至少区分：
- reasoning
- knowledge
- coding
- software engineering
- agentic / long-horizon tasks
- instruction following
- long context
- multimodal
- factuality
- tool use
- reliability
- latency
- cost

进一步学习：
- benchmark 是怎样设计的。
- pass@1 / pass@k。
- benchmark contamination。
- benchmark saturation。
- 测试时是否允许工具。
- reasoning effort 是否一致。
- Agent scaffold 是否一致。
- 为什么同一个模型在不同 coding agent 中表现可能差很多。
- 为什么公开榜单不能直接等于“哪个模型在我的任务里最好”。

推荐资源：
- SWE-bench / SWE-bench Verified：理解真实软件工程评测。
- METR：了解长时间自主任务 / Agent 能力评估。
- OpenAI 等厂商的 Evaluation / Evals 官方指南，可作为任务级评估方法参考。
- Artificial Analysis：作为模型横向数据参考，不把其综合分数当最终结论。

实践：
后期逐步建立自己的 vibe coding 小型 Eval 集。
任务来自真实开发，例如：
- 修复 bug
- 修改 UI
- 阅读陌生 repo
- 跨文件修改
- 处理构建错误
- 数据库修改
- 根据需求加入功能
- 根据截图调整页面

记录可包括：
成功率、第一次完成率、人工干预次数、失败类型、耗时、token/成本等。

第一遍只要求理解这种评估方法；完整自建 Eval 可放到开发基础提升以后。

5. AI 前沿跟踪

目标不是每天刷新闻，而是建立稳定来源。

优先来源：
- Stanford AI Index：年度行业大图景。
- Epoch AI：模型能力、算力和 benchmark 长期趋势。
- METR：Agent / autonomous task 能力研究。
- Artificial Analysis：最新模型横向数据。
- OpenAI / Anthropic / Google 等官方 model card / system card / technical report。

学序不要把“每日 AI 新闻”作为主学习任务。
建议后期设置轻量的每周或双周前沿回顾即可。

6. AI 第一遍的完成标准

完成第一遍后，应能回答：
- LLM 大致怎样从输入变成输出。
- token、context、embedding、Transformer 分别是什么。
- 模型与 Agent / Harness 有什么区别。
- RAG、Tool Calling、MCP 分别解决什么问题。
- 为什么不能只看一个 benchmark 判断模型。
- 为什么同一个模型在不同 coding agent 中可能差很多。
- 看一份新模型发布说明时，知道应该关注哪些指标和限制。


==================================================
四、第三条开发基础线如何衔接
==================================================

第三条线不要删除，也不要被前两条线取代。

沿用现有《开发学习方案》的主线：

01 编程基础（Python）
+ 03 编程与协作工具从第一天同步
→ 02 运行原理与操作系统
→ 04 数据结构与算法
→ 05 计算机网络与接口
→ 06 数据库与 SQL
→ 07 软件工程

它的作用是让用户逐渐从“会指挥 AI 开发”，进入：
能看懂关键代码
→ 能理解数据流和运行机制
→ 能判断实现方案
→ 能定位错误
→ 能自己修改简单部分
→ 能维护项目。

三条线关系必须在网站中明确表现为：

开发流程线 = 方法层
AI认知线 = AI领域认知层
开发基础线 = 底层实现能力层

前两条线应先建立第一遍地图，但不能无限停留在概念学习。
完成第一遍后，学习重点逐渐转向开发基础线。

随着开发基础线推进：
- 学到 Python / API 后，回到 AI 调用做真实实践。
- 学到网络后，重新理解 API / Tool Calling / MCP。
- 学到数据库后，重新理解 RAG、Memory、状态保存。
- 学到软件工程和测试后，重新学习 Agent Eval 和可靠执行。

之后再进入现有 AI 拓展的第二遍：
08 机器学习与深度学习基础
→ 09A 大模型基础与调用
→ 09B RAG、Agent 与 Harness

这一次不再只是“知道是什么”，而是要求能够实现、测试和评估。


==================================================
五、学序网站中的组织方式
==================================================

建议新增一个总学习领域，例如：
“AI与开发”

顶层显示三条线及其关系，不要把它们表现成三个互不相关的课程。

每个学习节点建议至少包含：
- 节点标题
- 学习目标
- 为什么现在学
- 核心内容
- 主资源
- 辅助资源
- 实践任务
- 完成标准
- 与真实项目的关联
- 前置/后续节点

开发流程线与 AI认知线允许并行。
开发基础线是长期系统主线。

不要把所有节点做成严格锁死的线性课程。
例如正在项目中遇到 HTTP、Git、数据库问题时，可以提前打开相关基础节点，但系统进度仍按主线记录。


==================================================
六、资源选择规则（重要）
==================================================

上面列出的教材和资源是当前推荐，不是绝对固定方案。

学序 Work 在真正写入网站前，应根据以下因素再次判断：
1. 用户当前基础。
2. 用户已有项目和最近实际遇到的问题。
3. 用户偏好系统学习，但不喜欢过度复杂的流程和追踪。
4. 优先使用一门主资源建立连续认识，其余资源只用于补充。
5. 能只学课程的一部分，就不要为了“完整”强制学完整门课程。
6. 官方文档适合查阅和实践，不一定适合承担零基础主课程。
7. 如果资源已经过时、章节调整或出现明显更好的官方资源，可以替换。
8. 英文/中文资源根据可理解性选择，不因“权威”牺牲学习效率。
9. 学习节点应以“理解并能用”为完成标准，而不是以“看完多少章节/视频”为标准。
10. 不要同时安排多个讲同一内容的完整课程。

资源建议层级：
主资源：负责建立连续框架，一次通常只选 1 个。
辅助资源：解释难点、查文档，一般 1—2 个。
项目实践：优先使用用户自己的序流、学序、sinefine、北京去哪儿玩等真实项目。
AI 辅助：用于解释、对比、复盘、分析错误，但不要替代实际验证。


==================================================
七、学习节奏和执行原则
==================================================

不要根据这份说明机械生成大量每日任务。

建议：
- 每个节点保持足够完整，不要切成大量五分钟碎片。
- 单次学习可以默认按约 30—60 分钟设计，但由学序根据用户时间进一步调整。
- 概念节点：理解 + 能用自己的话解释 + 一个具体例子即可。
- 实践节点：必须有一次真实操作或验证。
- 不要求每个知识点都有复杂考试、打分和复盘。
- 对明显重要的能力设置“完成标准”即可。
- 项目一直继续，不需要等课程学完才允许开发。

实际循环：

学习一个概念
→ 在当前项目中找到它
→ 实际操作或观察一次
→ 不懂的地方补知识
→ 回到项目继续使用。

最终目标不是让用户脱离 AI 手写整个项目，而是逐步扩大自己能够理解、判断、检查和接管的范围。

10. 实际开发时分阶段完成并验证，避免一次性大改。
